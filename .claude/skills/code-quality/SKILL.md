# コード品質ガイドライン（Python / JavaScript / TypeScript）

このスキルは、コードを新規作成・修正・レビューするすべての作業に適用する。
言語別の詳細は以下を必要に応じて読むこと。

- Python → `references/python.md`
- JavaScript / TypeScript → `references/typescript-javascript.md`
- 作業完了前の確認 → `references/review-checklist.md`（**完了報告の前に必ず読む**）

---

## 1. 作業の進め方

1. **既存コードに合わせる**: 変更前に周辺コード・設定ファイル（`pyproject.toml`, `package.json`, `tsconfig.json`, `eslint.config.*` など）を確認し、既存の規約・ライブラリ・ディレクトリ構成に従う。新しい依存ライブラリは、必要性を説明してから追加する。
2. **変更は最小限に**: 依頼された範囲だけを変更する。無関係なリファクタリングやフォーマット変更を混ぜない。気づいた別の問題は報告に記載する。
3. **小さく確認しながら進める**: 大きな変更は段階に分け、各段階でテスト・型チェックを通す。
4. **推測で進めない**: 仕様が曖昧な場合は、仮定を明記するか質問する。

## 2. 設計・可読性

- 関数は1つの責務に絞る。目安として50行・ネスト3段を超えたら分割を検討する。
- 早期リターン（ガード節）でネストを浅くする。
- マジックナンバー・マジック文字列は名前付き定数にする。
- 重複が3回以上現れたら共通化を検討する（2回までは無理に抽象化しない）。
- グローバルな可変状態を避け、依存は引数やコンストラクタで渡す。
- 副作用（I/O、DB、外部API）と純粋なロジックを分離し、ロジックをテストしやすくする。

## 3. 命名

- 名前は「何であるか／何をするか」が分かるものにする。`data`, `tmp`, `obj`, `flag` などの曖昧な名前は避ける。
- 真偽値は `is_` / `has_` / `can_`（JS/TSは `is` / `has` / `can`）で始める。
- 関数名は動詞で始める（`get_user`, `calculateTotal`）。
- 略語は一般的なもの（`id`, `url`, `api` など）以外使わない。

## 4. 型

- 新規コードには必ず型を付ける（Pythonは型ヒント、JSは可能ならTS化またはJSDoc）。
- `Any`（Python）／`any`（TS）は原則禁止。やむを得ない場合は理由をコメントに書く。
- 外部入力（APIレスポンス、ユーザー入力、ファイル、環境変数）は境界で検証してから内部の型に変換する。

## 5. エラー処理

- 例外を握りつぶさない（空の `except:` / `catch {}` は禁止）。
- 捕捉する例外は具体的な型に絞る。
- エラーメッセージには原因の特定に必要な文脈（対象ID、操作内容）を含める。ただし秘密情報は含めない。
- 回復できないエラーは上位に伝播させ、境界（APIハンドラ、CLIのエントリポイントなど）でまとめて処理する。

## 6. セキュリティ

- APIキー・パスワード・トークンをコードに直書きしない。環境変数やシークレット管理を使う。
- SQLは必ずパラメータ化する。文字列連結でクエリを組み立てない。
- `eval` / `exec` / `new Function` / `shell=True` などの動的実行は使わない。必要な場合は理由を説明する。
- ログに個人情報・秘密情報を出力しない。
- 外部から受け取ったパス・URL・HTMLはそのまま使わず、検証・エスケープする。

## 7. テスト

- 新しいロジックにはテストを追加する。バグ修正では、まずそのバグを再現するテストを書く。
- 正常系に加え、境界値・異常系（空、None/null、不正値）を最低1つずつ含める。
- テストは他のテストや実行順序に依存させない。外部サービスはモック／スタブにする。
- テスト名は「何を検証するか」が分かるものにする。

## 8. コメント・ドキュメント

- コメントは「なぜそうしたか」を書く。コードを読めば分かる「何をしているか」は書かない。
- 公開する関数・クラスにはdocstring／JSDocを付け、引数・戻り値・例外を記載する。
- `TODO` には理由と、可能なら課題番号を付ける。

## 9. 品質チェックの実行（必須）

作業完了前に、プロジェクトに設定されているツールを実行し、すべて通すこと。
設定ファイルやスクリプトがあればそれを優先する（例: `npm run lint`, `make check`）。

| 言語 | フォーマット | Lint | 型チェック | テスト |
|---|---|---|---|---|
| Python | `ruff format` | `ruff check` | `mypy` または `pyright` | `pytest` |
| JS/TS | `prettier` | `eslint` | `tsc --noEmit` | `vitest` または `jest` |

- ツールが未導入の場合は、勝手に導入せず、導入を提案する。
- 警告を抑制するコメント（`# noqa`, `# type: ignore`, `eslint-disable`, `@ts-ignore`）は原則使わない。使う場合は対象ルールを限定し、理由を書く。

## 10. 完了報告

作業終了時は以下を簡潔に報告する。

- 変更内容の要約（変更したファイルと目的）
- 実行したチェックとその結果（失敗が残っている場合は正直に書く）
- 仮定したこと、残っている課題、気づいた別の問題
