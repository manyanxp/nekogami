# 0008. 認証・認可の方針（Agent 365 型は導入しない）

- 状態: Accepted
- 日付: 2026-10-24

## 背景
Microsoft Agent 365 のようなエージェントの認証・認可制御が望ましいが、個人利用なら不要なら追加しなくてよい（要件 R4）。

## 決定
- 利用者の認証・ロール型の認可は**導入しない**。
- 代わりに最小限の防御を入れる:
  - 既定で `127.0.0.1` のみ待受。
  - `Host` / `Origin` の検証（DNS リバインディング・他サイトからの操作対策）。
  - 変更系 API は `Content-Type: application/json` 必須（フォーム送信による CSRF を防ぐ）。
  - 任意の共有トークン: `PORTAL_TOKEN` を設定すると `/api/*`（health 以外）が `Authorization: Bearer` 必須になる。
- Docker 操作は、台帳に登録済みの compose ファイル・サービスに限定（ADR 0009）。

> 2026-10-25: 複数人で使うようになり、ローカルアカウントによるログインとロールを導入した（[0035](0035-login-and-roles.md)）。共有トークンはスクリプト用に残る。

## 再検討の条件
複数人で使う、LAN/インターネットに公開する、エージェントごとに操作権限を分けたい場合は、ID 基盤（例: Microsoft Entra ID）による認証と、エンティティ単位のロール（閲覧 / 操作 / 管理）を新しい ADR で設計する。Agent 365 の機能・提供状況は導入前に最新ドキュメントで確認すること（現時点では未確認）。

## 影響
- 個人利用では追加の手間がない。ただし `PORTAL_HOST=0.0.0.0` にする場合は `PORTAL_TOKEN` と TLS 付きプロキシを必須とする。
- 関連: `portal/backend/portal_api/server.py`
