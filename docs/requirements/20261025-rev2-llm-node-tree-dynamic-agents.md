# 要件資料: LLM ノード、Python ノード、サブオーケストレーターの入れ子、担当のツール化、足りないときの自動作成（rev2）

- 元資料: `docs/add_requirement/2026-10-25/2026-10-25.add_requirement_rev2.md`（Git の管理対象外）
- 日付: 2026-10-25 / 状態: **第 1・2 段階（LLM ノード、Python ノード）が実装済み**。第 3・4 段階は未着手（rev2 は 2026-10-25 に、要求 6〜7 を追加）

## 1. 目的
ローカル LLM を、他の担当から使える部品にする。Python の関数を、引数つきのツールノードとして使えるようにする。サブオーケストレーターを入れ子（ツリー）にできるようにし、担当をツールとして呼べるようにする。担当が足りないときは、自動で一時的な担当を作って使い、終われば消す。

## 2. 要求と対応

| # | 要求 | 対応 | 段階 / 決定 |
|---|---|---|---|
| 1 | ローカル LLM を、他のサブオーケストレーター・エージェントから呼べる。ノードで接続できる | 「LLM ノード」（ツールの一種）を新設。担当へワイヤーでつなぐと、`ask` ツールで質問できる。Ollama の API を直接呼ぶ | 第 1 段階（実装済み）。ADR 0040。決定: 別セッション型ではなくツール型 |

## 5. 未確認・リスク
- 第 1 段階: LLM ノードは会話だけで、ツールもファイルも使えない。文脈は 16K。精度は Claude より落ちる（ADR 0039）。
- 第 1 段階: サブオーケストレーターへの接続は、委任先（type=agent）の担当の定義に反映される。猫神さまや、委任先のないサブオーケストレーターには、つなげない（つないでも効かないため、登録時に拒否する）。委任先の担当を直接呼んでも、同じノードが使える。
- 第 2 段階: 関数のコードは、管理者がノードに書き、`py-sandbox`（ネットワークなし・30 秒・512 MB）で動く。引数は担当が渡すので、型の検査と、JSON での受け渡しで守る。
- 第 3 段階: 入れ子が深いほど、費用・時間・失敗の連鎖が増える。
- 第 4 段階: 担当を担当が呼ぶ仕組みは、費用・時間・無限の呼び合いのおそれがある（深さと回数の上限を持たせる）。自動作成の担当が増えすぎないよう、数と権限に上限を持たせる。
